# Argo CD Hub-and-Spoke Lab

## 1. Purpose

This repository is a small, educational lab demonstrating a production-representative **Argo CD hub-and-spoke multi-cluster architecture**.

The lab must remain:

* Small
* Easy to understand
* Easy to rebuild
* Easy to demonstrate
* GitOps-driven
* Representative of production architecture

Do not add unnecessary components or complexity.

The goal is to **fake the infrastructure, not the architecture**.

Local technologies such as k3d and Moto replace cloud infrastructure, while the Argo CD, Kubernetes, GitOps, RBAC, ApplicationSet, and External Secrets architecture should remain representative of a real production deployment.

---

# 2. Architecture

The lab consists of three Kubernetes clusters:

```text
                    Git Repository
                         |
                         | desired state
                         v
               +--------------------+
               |   argocd-hub       |
               |                    |
               |     Argo CD        |
               |   ApplicationSet   |
               +---------+----------+
                         |
                         | Kubernetes API
                  +------+------+
                  |             |
                  v             v
          +---------------+ +---------------+
          |   spoke-01    | |   spoke-02    |
          |               | |               |
          | demo app      | | demo app      |
          | ESO           | | ESO           |
          +-------+-------+ +-------+-------+
                  |                 |
                  +--------+--------+
                           |
                           v
                  +----------------+
                  |      Moto      |
                  |                |
                  | Fake AWS       |
                  | Secrets Manager|
                  +----------------+
```

Cluster names:

```text
argocd-hub
spoke-01
spoke-02
```

Use **k3d** unless there is a strong technical reason to use kind.

Argo CD runs only in:

```text
argocd-hub
```

The spoke clusters must NOT run their own Argo CD instances.

# 3. Production Architecture Being Modeled

The local lab represents approximately:

```text
LOCAL                         PRODUCTION

k3d argocd-hub       ->       Management EKS cluster
k3d spoke clusters   ->       Workload EKS clusters
Docker networking    ->       VPC/network connectivity
Moto                  ->       AWS Secrets Manager
Local credentials    ->       IAM / workload identity
Git repository       ->       Production Git repository
```

Do not simplify Argo CD behavior merely because the infrastructure is local.

The following concepts should remain real:

* Argo CD remote cluster registration
* Kubernetes API communication
* ApplicationSet
* Cluster Generator
* Git reconciliation
* automated synchronization
* self-healing
* cluster labels
* RBAC
* External Secrets Operator
* ExternalSecret resources
* Kubernetes Secrets generated by ESO

# 8. Cluster Creation

Use k3d.

Expected clusters:

```bash
k3d cluster create argocd-hub
k3d cluster create spoke-01
k3d cluster create spoke-02
```

Scripts may automate creation, but commands should remain easy to understand.

After creation, verify:

```bash
kubectl config get-contexts
```

Expected contexts should include the hub and both spokes.

---

# 9. Argo CD Hub

Install Argo CD only in:

```text
argocd-hub
```

Namespace:

```text
argocd
```

The hub must manage remote spoke clusters using their Kubernetes APIs.

Do not install Argo CD controllers on the spokes.

Conceptually:

```text
Argo CD Application Controller
             |
             +------> spoke-01 API
             |
             +------> spoke-02 API
```

---

# 10. Remote Cluster Registration

The spoke clusters must be registered with Argo CD.

Argo CD cluster registration should result in cluster credentials/configuration represented as Kubernetes Secrets in the `argocd` namespace.

Where practical, show both:

```text
argocd cluster add
```

and the underlying declarative Secret model.

The user should understand what `argocd cluster add` actually creates/configures.

---

# 11. Cluster Labels

Registered clusters should contain labels that ApplicationSet can use.

Example:

```yaml
metadata:
  labels:
    environment: dev
    workload: applications
```

Optional future labels:

```yaml
region: local
team: platform
```

Do not hardcode individual cluster names in ApplicationSets when label selection can demonstrate the intended architecture more clearly.

---

# 12. ApplicationSet

Use an Argo CD ApplicationSet with the **Cluster Generator**.

Conceptually:

```yaml
generators:
  - clusters:
      selector:
        matchLabels:
          workload: applications
```

The ApplicationSet should automatically generate an Argo CD Application for every matching spoke cluster.

Expected behavior:

```text
spoke-01 registered
       |
       v
Application generated
       |
       v
demo app deployed


spoke-02 registered
       |
       v
Application generated
       |
       v
demo app deployed
```

The ApplicationSet should NOT require modification when another matching spoke is added.

---

# 13. Important Scaling Demonstration

The lab should eventually support:

```bash
./scripts/create-spoke.sh spoke-03
```

After registering and labeling `spoke-03`, ApplicationSet should automatically create the corresponding Application.

The intended demonstration is:

```text
new cluster
    |
register
    |
label
    |
ApplicationSet discovers cluster
    |
Application generated
    |
application deployed
```

No modification to the ApplicationSet should be necessary.

This is one of the most important demonstrations in the lab.

# 14. Demo Application

The application must remain extremely simple.

Prefer:

* nginx

Avoid building application complexity.

The application should make it easy to verify:

```text
Cluster: spoke-01
Environment: dev
Secret loaded: yes
```

# 15. External Secrets

Install External Secrets Operator on the spoke clusters.

Conceptual architecture:

```text
Git
 |
 | ExternalSecret
 v
Argo CD
 |
 v
Spoke Cluster
 |
 | reconciliation
 v
External Secrets Operator
 |
 | AWS Secrets Manager API
 v
Moto
 |
 v
Kubernetes Secret
 |
 v
Application Pod
```

Git contains the secret reference.

Git must NOT contain the secret value.

---

# 16. Moto

Use Moto running as a Docker container to emulate AWS Secrets Manager.

Conceptually:

```text
Docker Host

├── k3d-argocd-hub
├── k3d-spoke-01
├── k3d-spoke-02
└── moto
```

Moto represents:

```text
AWS Secrets Manager
```

Create a simple secret such as:

```text
/demo/database
```

with fields such as:

```text
username=demo-user
password=super-secret
```

These values must NOT be committed to Git.

The repository may contain scripts that populate Moto at lab startup.

---

# 17. External Secrets Configuration

Use External Secrets Operator resources such as:

```text
SecretStore
```

or:

```text
ClusterSecretStore
```

and:

```text
ExternalSecret
```

Prefer `SecretStore` initially when namespace-scoped access is sufficient.

Avoid unnecessarily broad cluster-wide permissions.

# 18. Security Principles

Even though this is a lab, model good production practices.

## Secrets

Never commit plaintext application secrets.

Bad:

```yaml
password: super-secret
```

Good:

```yaml
remoteRef:
  key: /demo/database
  property: password
```

## Argo CD Permissions

Avoid giving remote Argo CD access unrestricted `cluster-admin` permissions unless absolutely required for an explicit lab step.

Prefer least privilege.

The lab should eventually demonstrate that Argo CD can manage only the resources/namespaces it needs.

## Argo CD Projects

Use an `AppProject` when appropriate to demonstrate boundaries around:

* allowed Git repositories
* destination clusters
* destination namespaces
* resource types

Keep the first implementation simple.

---

# 19. Sync Policy

Applications should eventually demonstrate:

```yaml
syncPolicy:
  automated:
    selfHeal: true
```

Use pruning deliberately.

Do not blindly enable deletion behavior for every resource.

Explain the implications before enabling:

```yaml
prune: true
```

The lab should demonstrate drift correction.

For example:

```bash
kubectl scale deployment demo-app --replicas=5
```

Argo CD should detect drift and restore the Git-defined replica count when self-heal is enabled.

---

# 20. GitOps Rule

Git is the desired-state source of truth.

After bootstrap, avoid manually modifying managed Kubernetes resources.

Bad workflow:

```text
kubectl edit deployment
```

as a permanent configuration mechanism.

Good workflow:

```text
edit Git
   |
commit
   |
push
   |
Argo CD reconciles
```

Manual modifications may intentionally be performed to demonstrate drift/self-healing.

---

# 21. Bootstrap Boundary

Not everything can initially come from Argo CD.

The lab should clearly distinguish:

```text
BOOTSTRAP
```

from:

```text
GITOPS-MANAGED STATE
```

Bootstrap includes things required before Argo CD can manage the environment, such as:

* creating k3d clusters
* installing the initial Argo CD instance
* initial spoke registration
* starting Moto

After bootstrap, move as much configuration as reasonably possible under GitOps.

Do not hide this bootstrap boundary.

---

# 22. Networking

Argo CD must communicate with the Kubernetes API of each spoke.

ESO running inside each spoke must communicate with Moto.

Do not assume `localhost` means the Docker host from inside Kubernetes pods.

Explicitly verify connectivity.

Useful tests include:

```bash
kubectl get nodes
```

against each context and temporary network/debug pods when necessary.

Keep Docker/k3d networking configuration documented.

# 24. Failure Demonstrations

Where useful, intentionally demonstrate failures.

Examples:

## Git drift

Modify a Deployment manually and observe Argo CD repair it.

## Secret unavailable

Stop Moto and observe ESO reconciliation failure.

## Cluster unavailable

Stop one spoke and observe Argo CD report the cluster as unavailable without affecting the other spoke.

## New cluster

Add `spoke-03` and demonstrate ApplicationSet automatic discovery.

These demonstrations are valuable because they explain the architecture better than a successful deployment alone.

# 27. Codex Working Rules

When modifying this repository:

1. Inspect the existing repository before creating files.
2. Do not overwrite working configuration unnecessarily.
3. Keep YAML small and readable.
4. Prefer standard Kubernetes and Argo CD patterns.
5. Avoid premature abstraction.
6. Avoid unnecessary Helm charts.
7. Use Helm when it provides clear value, such as installing upstream software.
8. Explain significant architectural changes.
9. Provide verification commands after changes.
10. Keep commands compatible with a local developer workstation.
11. Never commit credentials or secret values.
12. Prefer declarative configuration over imperative commands after bootstrap.
13. Do not introduce additional platform components without explaining why they are necessary.
14. Preserve the hub-and-spoke architecture.
15. Keep the lab understandable by someone learning Argo CD.

# 28. Before Making Major Changes

Before introducing a new major component, answer:

```text
Why do we need it?

What production concept does it demonstrate?

Can the same concept be demonstrated more simply?

Does it obscure the hub-and-spoke lesson?
```

If the component does not materially improve the lab, do not add it.

# 29. Primary Learning Objectives

At the end of the lab, the user should understand:

1. What an Argo CD hub-and-spoke architecture is.
2. Why Argo CD does not need to run on every spoke.
3. How the hub authenticates to remote Kubernetes clusters.
4. How Argo CD stores registered cluster information.
5. How ApplicationSet discovers registered clusters.
6. How cluster labels control application placement.
7. How one Git definition can deploy across multiple clusters.
8. How Argo CD detects and repairs drift.
9. How External Secrets separates secret references from secret values.
10. How ESO retrieves secrets from AWS Secrets Manager.
11. How the local Moto implementation maps to real AWS Secrets Manager.
12. What the security/blast-radius implications of centralized Argo CD are.
13. How the architecture could later evolve toward multiple Argo CD instances or an agent-based model.

---

# 30. Most Important Rule

Do not optimize this lab for the fewest commands.

Optimize it for understanding.

The desired outcome is not:

> "The deployment worked."

The desired outcome is:

> "I understand exactly why the deployment worked, how the hub manages the spokes, where credentials and secrets live, how ApplicationSet discovers clusters, and how this design maps to a production multi-cluster Argo CD architecture."
